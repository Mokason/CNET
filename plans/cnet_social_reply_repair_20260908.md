# Identity, presence and Discord reply repair

## Contract and decision

Identity/presence is a whole request, not any sentence containing "you" and
"language model", or the prefix "what are you". Bound aliases and legacy
catalog matches consistently, including case variants, compound requests and
truncation. Keep real identity and greeting routes. Do not change capsule
certification, acquisition or coverage floors.

Closed operational help explains how to call skills and the independent-evidence
requirement for learning. It does not start a job, imply a running learner or
claim measured improvement. Inventory reports raw LUTs separately from certified
capsules. Unknown requests retain their miss/verification flags and get an honest
next step rather than a social filler response.

Discord uses the existing native peer JSON interface. Add optional peer request
support and escaped peer/stage response metadata; preserve strict framing and
bounded sizes. Reject duplicates, wrong types, incomplete replies and overflow.
Display the answer, retaining refusal and source qualifiers; never raw teachers.
An eligible STAGE draft is visibly unverified. Do not heuristically censor words
such as CNET, operator names or "not certified". The ambiguous multiline line
protocol remains for existing CLI callers, not Discord presentation.

## Sequence

1. Reproduce with native requests and the scoped owner capture chronology.
2. Capture RED alias, native process, presentation and JSON transport tests.
3. Implement bounded routing and truthful presentation, then run native-to-Discord
   synthetic integration and existing capture/protocol/coverage gates.
4. Fresh-context Astra reviews under the doubt-driven skill. Owner's Astra-only
   preference excludes external model CLIs. Reconcile findings before rollout.
5. Backport only the relevant six runtime source/header files into the older live
   baseline, preserving existing dirty changes. Build in a separate private release
   linked against the unchanged live capsule library. Stage the native peer and
   complete frozen capture release together; no in-place runtime replacement.
6. Use dedicated user-service overrides for daemon, bridge and matching monitor/
   watchdog release. Preserve tokens, scope, data and existing overrides. Capture
   observation continuity restarts honestly for the changed release. Check real
   native replies through the same deployed Discord renderer without injecting
   synthetic messages into the owner-demand dataset.

## Rollback and limits

Keep source/runtime originals and old releases. Move only this repair's four new
service overrides into its private backup; daemon-reload and restart the daemon
and bridge. Existing monitor/watchdog timers select their previous release at the
next tick. Do not reset the checkout, delete knowledge or reset observation history.

This is a scoped routing/IO repair, not new learned domain knowledge or proof of
unattended improvement. Unsupported questions still abstain. Arbitrary compound
intent composition, legacy non-JSON CLI framing and broader runtime authorization
remain outside this gate. No remote push is requested in this turn.
